## 一、必须改

### 1. [blocker] Deck 步进开销远超第四幕预算
- **文件:行：** `GateClouds/Shaders/Lanbai_GateCloudDeck.shader:205-320`（步进循环 248-299，Field 145-196）
- **问题：** 每个向下看的像素先做一次 `Field(r, ts)`。然后是 `for (int s = 0; s < 160; s++)`，上限 `_Steps = 120`，`_StepK = 0.02`，`_MarchRange.y = 1600`。之后还有 5 次二分，再加一次 `Field(r, tHit)`。每次 Field 取 3 次 `tex2Dgrad`（detail、macro、micro），另有 exp2/log2/sqrt/exp 和若干 smoothstep、除法。
- **证据：**
  - 在临时副本里跑了 `Source/deck_ref.py`。平均步数 / p90：U7 30.2/40，U8fwd 24.8/31，U8side 26.9/36，key 23.8/35。向下看的像素约占画面 0.33-0.50。和 README §3.4 自己给的数字一致：平均 21-30 步，p90 33-41。
  - 合计每像素约 30-37 次 Field、约 100-110 次采样。
  - 粗估（RTX 4060L、9.03 MP）：ALU 约 3 ms 起，三线性/各向异性采样约 3-6 ms 以上，低端也在 3 ms 以上。
  - 账本 §1.1：没有云的情况下门已约 8.6 ms，第四幕热点上限是 7.1 + 1.2 = 8.3 ms。圣经 §1.9 给 U8 云海 0.9 FSE，按门的填充率 0.24 ms/MP 约合 1.9 ms。
  - 包里没有给任何 ms 数字，README 第 103 行把测量留给了 Unity。
  - 两个因素让实际开销更大：16x 各向异性（见第 4 条）、SV_Depth 关掉了 early-Z（见第 3 条）。
- **怎么改：** 第四幕合入前，Deck 必须带上实测的 ms 和 FSE，测法按 gate_test / 账本 §3，有 Deck 和无 Deck 各测一次。目标是 VR 下不超过约 1-1.5 ms。以下各项可以叠加，按顺序做：
  1. 第 39-41 行改默认值：`_Steps` 64，`_StepK` 0.035，`_MarchRange.y` 700，超出部分交给现有的远处均值平面回退。deck_ref 在 U7 实测：平均步数 30.2→17.9，p90 40→23，APL 29.3→28.8。deck_ref.py 同步修改。
  2. 各向异性上限改为 4（见第 4 条），Field 里的 `across * 16.0` 改为 `across * 4.0`。
  3. Field 里先算 `lodU`/`fade`，`fade == 0` 时跳过第三次 tex2Dgrad，`mu` 直接取 0.45。
  4. 最后一次二分得到的 `Field(r, hi)` 结果直接复用，不再算一次 `Field(r, tHit)`。`tm > 400` 时只做 3 次二分。
  5. 恢复 early-Z（见第 3 条）。
  6. 如果还超：半分辨率渲染加深度感知上采样，或者把 1 km 以外的云海烘进第四幕天空或静态卡环。

  实测数字写进 README_GateClouds.md §3.4 和账本里第四幕的条目。

### 2. [major] 云卡 billboard 的 right 轴朝向观察者左边，所有卡都镜像了
- **文件:行：** `GateClouds/Shaders/Lanbai_GateCloudCard.shader:111-114`；`GateClouds/Source/preview_gate.py:110-112`
- **问题：** 代码是 `float3 toEye = CentreEye() - pivot; float2 f = normalize(toEye.xz ...); float3 right = float3(f.y, 0.0, -f.x);`。
- **证据：**
  - 设眼在原点、pivot 在 (0,0,10)。得到 f=(0,-1)，right=(-1,0,0)。Unity 里朝 +Z 看，屏幕右边是 +X，所以 right 指向了左边。
  - CardQuad（Builder:129-130）把 uv.x=1 放在 x=1-pu，于是贴图右列跑到观察者左边。
  - 烘焙时月亮确实在贴图右侧（make_clouds.frame_camera、gate_cards.moon，PNG 没有翻转）。
  - gate_clouds_layout.py:63-65 用 `right = (lz, -lx)` 选 `mirror`，这是对的。结果是 shader 把每张卡的 mirror 含义都反过来了。
  - frag 只按无符号角选 R/G，不会纠正。前向散射的 lining 在世界空间算，位置是对的。所以银边背着月亮，lining 却亮在另一侧。
  - Cull Off 掩盖了这个问题，preview_gate.py 抄了同一套约定，预览图也看不出来。
- **怎么改：**
  - shader 改为 `float3 right = float3(-f.y, 0.0, f.x);`，注释一起改。
  - preview_gate.py:112 改为 `right = np.array([-f[1], 0.0, f[0]])`。
  - layout 的 mirror 规则和烘焙不动，这两者本来一致。
  - 在 Unity 里拿一张 mirror=0、月亮方位已知的卡验证：亮的 G/R 侧应该朝向月亮。

### 3. [major] Deck 输出 SV_Depth，early-Z 失效，被遮住的像素也跑完整步进
- **文件:行：** `GateClouds/Shaders/Lanbai_GateCloudDeck.shader:82-84, 91, 205, 329`；`GateClouds/Source/gate_clouds_layout.py:107, 113`；`README_GateClouds.md:72`
- **问题：** 结构是 `struct FOut { half4 col : SV_Target; float depth : SV_Depth; };`。普通 SV_Depth 会关掉 early depth 拒绝。Queue 是 Geometry+40，排在大巴、触手、裂口之后，但它们已经盖住的像素照样跑完整步进和着色。第 82 行注释说"顺序只影响 overdraw"，这个前提不成立。
- **证据：** quad 放在云层最底下（`local_y=round(y_bot, 2)`，y_bot 比场的最低点还低 5 m），所有命中点都比 quad 近。现在这个位置用不了任何 conservative depth 语义，quad 得先挪。
- **怎么改：**
  1. 在顶点着色器里把 quad 抬到云层顶，并压在眼睛下方：
     ```
     float top = CloudTop();
     float yTop = top + _DetailRange.w + _DetailRange.y * _AmpRange.y;
     o.wpos = mul(unity_ObjectToWorld, v.vertex).xyz;
     o.wpos.y = min(yTop, _WorldSpaceCameraPos.y - 0.05);
     o.pos = UnityWorldToClipPos(o.wpos);
     ```
     射线都向下，所有命中点都在 quad 上或更远。
  2. 改用 conservative depth，`#pragma target 5.0`（项目只出 PC/Link，可以用）：
     ```
     #if defined(UNITY_REVERSED_Z)
       #define DECK_DEPTH SV_DepthLessEqual
     #else
       #define DECK_DEPTH SV_DepthGreaterEqual
     #endif
     struct FOut { half4 col : SV_Target; float depth : DECK_DEPTH; };
     ```
     `SHADER_TARGET < 50` 时保留普通 SV_Depth。
  3. Queue 仍用 Geometry+40，第 82 行注释改为"使用 conservative depth，所以绘制顺序有意义"。
  4. 同步修改 gate_clouds_layout.py:113 和 README §3.1 里"y = −176.6 … 整个云层的最下面"那句，quad_size 不变。deck_ref 如果读 local_y 就复查一下。
  5. 可选：frag 里加 `t0 = max(t0, dot(i.wpos - r.ro, r.V))`。
  6. 用 README 要求的帧时测法，在第四幕主机位对比改前改后。

  注：shaders 组原来建议"quad 留在底部，reversed-Z 下用 SV_DepthGreaterEqual"。那样写出的深度比光栅化深度更近，硬件仍然不能提前剔除。第 1 条第 5 项里"SV_DepthGreaterEqual"的写法也是同一个问题。以本条的方向为准：先抬 quad，再在 reversed-Z 下用 SV_DepthLessEqual。

### 4. [major] Deck 贴图开 16x 各向异性，每步 3 次采样全是各向异性
- **文件:行：** `GateClouds/Editor/LanbaiGateCloudsBuilder.cs:88`；shader Field 约 153-195
- **问题：** 代码是 `ti.anisoLevel = repeat ? 16 : 2;`，两张 Deck 贴图的 repeat 都是 true。Field 给 tex2Dgrad 传了真正的各向异性梯度：`along = min(across / max(r.vy, 0.02), across * 16.0)`。步进和二分每次都调 Field，单像素最多约 165×3 次各向异性采样。
- **证据：** 实测各向异性比 min(1/vy,16)：U7/U8fwd 平均 6.3，U8side 8.4，key 10.6，26-60% 的像素在 8x 以上。步进和二分其实只用到清距 `.c`。deck_ref.py:209 验证的是各向同性几何平均 LOD，它自己注明这是有意的近似。
- **怎么改：**
  - 把 Field 拆成两个版本。
    - 一个只算清距，给步进、cPrev 和二分用，全部换成 tex2Dlod：`lodD = log2(max(s.foot / (_Periods.x * _DetailTex_TexelSize.x), 1e-4)) + _LodBias`，macro 和 micro 同理（micro 直接用已有的 `lodU`）。这样和 deck_ref.field() 完全一致。
    - 各向异性的 tex2Dgrad 只留给最后一次着色用的 `Field(r, tHit)`。
  - Builder:88 改为 `repeat ? 4 : 2`。重渲后只在 U8side 或 key 镜头明显发糊时才往上调。
  - 高度图保持未压缩 RGBA32。README:56 说明了压缩会出块，所以**不要**改 BC7。
  - 在参考 GPU 上重测第四幕 U8，记入 perf.txt。

### 5. [major] Deck 不进 `_CameraDepthTexture`，云海处的软深度淡化全部变硬边
- **文件:行：** `GateClouds/Shaders/Lanbai_GateCloudDeck.shader:83-86, 205, 335`
- **问题：** 只有一个没有 LightMode 的 Pass，最后是 `FallBack Off`，没有 ShadowCaster。ART_BIBLE 第 165 行要求每幕都有带阴影的实时主光，所以 `_CameraDepthTexture` 存在，它由不透明物体的 ShadowCaster pass 画出。Builder 第 208 行把 Cast Shadows 设成 Off，但这类 pass 照样会跑。Deck 没有这个 pass，深度图里记的是云海背后的天空。
- **证据：**
  - 受影响的地方：
    - Lanbai_Tear.shader:448-450（_PART_SHAFT）和 511-514（_PART_FOLDS）的 `LinearEyeDepth(SAMPLE_DEPTH_TEXTURE_PROJ(_CameraDepthTexture, ...))`；
    - 云卡 158-165（注释写的是"云浪切开卡片处的软深度淡化"）；
    - 光束 97-100。
  - 这些地方读到的 sceneZ 都极大，永远不淡化。硬件 ZTest 照样按 Deck 的深度切，所以边缘是硬的。
  - README:135 和 §3.1 的说法因此做不到。
  - 缓和因素：云卡 `_SoftFade` 默认是 0，底部有解析式融化；Tear CloudGlow 用解析的 `CloudFootFade`。眼下实际受影响的是 Tear 的 shaft/folds。
- **怎么改：** 在 `FallBack Off` 前加一个 Pass，`Tags { "LightMode"="ShadowCaster" } ZWrite On ZTest LEqual Cull Off ColorMask 0`，再加 `#pragma multi_compile_shadowcaster`。
  - 复用主 pass 的顶点着色器和 stereo 宏，读 `_WorldSpaceCameraPos` 前先调 `UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX`。
  - frag 跑和主 pass 相同的高度场步进。把它抽成共用函数，放进 cginc 或 CGINCLUDE。步数上限约 32，`_StepK` 不变，2-3 次二分，不做 skin、光照和雾。
  - 未命中和向上射线的处理和主 pass 一致。
  - 深度输出 `c.z / c.w`，其中 `c = UnityWorldToClipPos(hit)`。
  - 近处**不要**用均值平面 `r.top + _MarchRange.z` 代替，否则淡化会和真实的云浪遮挡对不上。均值平面只用在主 pass 本来就回退的地方。
  - Builder 里 Cast Shadows 保持 Off，这个 pass 就只进相机深度 prepass。
  - README §3.4 注明：帧时测量要把这次 prepass 的开销算进去。这个 pass 也要按第 3 条的方式写深度。
  - 验证：在 Frame Debugger 里确认 UpdateDepthTexture 画了 Deck。第四幕开 `SOFTPARTICLES_ON` 看 Tear 的 shaft/folds，再看一张 `_SoftFade` = 30 m 的卡。

## 二、建议

1. **云卡和光束的软淡化用材质 float 开关，不是 SOFTPARTICLES_ON。** 位置：`Lanbai_GateCloudCard.shader:35, 62-65, 161-165`，`Lanbai_GateBeam.shader:34, 45-47, 97-101`。ART_BIBLE:165 要求自定义深度淡化一律用 `#pragma multi_compile _ SOFTPARTICLES_ON`，关掉时回到硬边，Tear 和 Rain 都是这么做的。现在默认值是 0，不会出事，但 README:135 建议设成 20-40 m，照做以后，没有深度图的客户端上卡片会消失或者不淡化。
   - 改法：加上这个 pragma，把 `if (_SoftFade > 0.0) {...}` 包进 `#if defined(SOFTPARTICLES_ON)`。可选：把深度图声明和 `i.proj` 的计算也挪进同一个块。
   - 同步修改属性注释和 README:135。和第一节第 5 条一起做。
2. **lining 在 `_Lining.z` 处是硬截断，月亮周围有一圈亮度台阶。** 位置：`Lanbai_GateCloudCard.shader:149`，`preview_gate.py:136`。代码是 `* step(am, _Lining.z)`，默认值 (0.9, 7, 15)，在 15° 处月光项从 ×1.105 跳到 ×1.0。经过雾和 alpha 削弱后，半透明边缘上仍有 2-5% 的台阶，正好落在美术要看的银边上。
   - 改法：换成连续衰减，二选一。
     - (a) `_Lining.x * max(exp(-am/_Lining.y) - exp(-_Lining.z/_Lining.y), 0.0) * edge`；
     - (b) `* (1.0 - smoothstep(0.6*_Lining.z, _Lining.z, am))`。
   - preview_gate.py 做同样的修改，保证两边逐位一致。
3. **37 张卡和 6 束光没有 FSE 或 overdraw 数据，算这些需要的布局 JSON 也没提交。** 位置：`README_GateClouds.md:103`，`给总控.md`。分支上没有 `GateClouds_Layout.json`，也没有 `Textures/gate_cards.json`，所以布局脚本报 FileNotFoundError。账本 §1.3 要求每个包报自己透明层的 FSE。STATUS.md 已经把这部分排在里程碑 2，所以算 minor。
   - 里程碑 2 要做：
     - 提交这两个 JSON。
     - 仿照 gate_fse.py，在 U7b、U8、U8+3.5、U8+7 做逐层覆盖遮罩，按 Deck 做深度剔除，结果写到 `final/fse_clouds.json`。
     - 对照的线：卡 ≤ 0.9，shaft+wedge ≤ 0.7，单像素 ≤ 8 层，第四幕合计 4.0（含车窗玻璃 0.7）。
     - 超了就合并或收窄地平线卡和远卡，alpha < 0.05 时关掉 renderer。
4. **时间窗写死成秒数。** 位置：`Runtime/LanbaiGateClouds.cs:62-64`，`LanbaiGateCloudsBuilder.cs:317`。`{ 113.80f, 181.55f }` 就是 U6−20 和 U9+2，违反 CONTROL §3 和集成 §4。其余曲线都从 cues 烘焙进来，只有窗口没走这条路，以后调 cue 时会对不上。
   - 改法：
     - layout.py 把 `"window": [CUES['U6']-20, CUES['U9']+2]` 写进 JSON，−20 和 +2 定义成具名常量。
     - Builder 把它拷到驱动的 `public float[] window`，`LanbaiWindow()` 直接返回这个数组。
     - 第 317 行改为 `Apply(Load(KitDir()).hero_t)`。
     - Tools~ 里加一条一致性检查。
5. **README 的接入步骤和 §5 接口矛盾，全局变量也没列全。** 位置：`README_GateClouds.md:60, 64`，`Lanbai_GateCloudDeck.shader:20-21`。第 60 行写的是 Director 每帧 `gateClouds.t = t; gateClouds.Apply();`，应改为由分发层登记，在窗口内调 `LanbaiTick(t)`、在遮挡下调 `LanbaiActivate(on)`。第 64 行和 shader 头注释漏了 `_Udon_TearH`、`_Udon_TearFoot`，应列全 6 个。给总控.md 里加一条请求：在 `Common/UdonGlobals.md` 这 6 个变量的"读的"一栏补上 GateClouds。

7. **驱动关掉的是它自己所在的物体**（`LanbaiGateClouds.cs` 的 `LanbaiActivate`：`gameObject.SetActive(on)`）。Director v1（pkg/engineering 的 `Director/`，`README_Director.md` §3）的规矩是：**驱动挂在永远激活的物体上，`LanbaiActivate` 开关另一个根**——物体关掉以后，这个 UdonBehaviour 还能不能收到下一次 `LanbaiActivate(true)` 取决于 VRChat 的实现，不能赌。改：加 `public GameObject root;`（= GateClouds 的根），`LanbaiActivate` 只 `root.SetActive(on)`；Builder 把驱动挂到 `Lanbai/Director` 下面（或者 GateRoot 外面一个常开的物体上）。分发层的 **2 Wire Scene** 菜单会提示挂在未激活物体上的驱动。
