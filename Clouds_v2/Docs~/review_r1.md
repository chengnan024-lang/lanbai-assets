## 一、阻断

### B1 · 公告板左右反了：卡在 Unity 里是镜像显示的，受光面会朝背离太阳的一侧（阻断）
`Lanbai_CloudCard.shader` 第 104–105 行：
```hlsl
float2 f = normalize(toEye.xz + float2(1e-5, 0.0));     // f = 枢轴 → 眼
float3 right = float3(f.y, 0.0, -f.x);                  // 注释写的是“从眼看过去，卡的 +x 在右边”
```
Unity 是左手坐标系（x 右、y 上、z 前）。举个例子：眼在原点、卡在 (0, 0, 100)，这时 f = (0, −1)，算出来 right = (−1, 0, 0)，也就是**看的人的左边**。再换一个方向验证：卡在 (100, 0, 0)，f = (−1, 0)，right = (0, 0, +1)，人朝 +x 看的时候 +z 在左边，还是反的。网格上 x = +0.5 那个顶点的 uv.x = 1，所以贴图的右边缘被画到了人的左边。

门的 `Lanbai_GateCloudCard.shader` 第 111 行写的是 `right = float3(-f.y, 0.0, f.x)`，旁边注释 “tech r1 #3” 说明门当时就是在这里修过同一个 bug。v2 又把它写反了。

后果：贴图是按“太阳在视线右侧”烘的，`_Mirror` 自动模式也按这个约定判断，结果每张卡在 Unity 里都是镜像的，受光面和银边都跑到了背离太阳那一侧。`cardshade.py` 只在图像空间里着色，不模拟顶点的朝向，所以总览图查不出这个问题。
**改法**：改成 `float3 right = float3(-f.y, 0.0, f.x);`，注释照门的写。改完以后，`_Billboard 0` 模式也要按 B2 / S5 的约定重新检查一遍。

### B2 · 网格尺寸约定前后不一致：照 README 摆，卡会被纵向拉伸或压扁（阻断）
- shader 文件头和 README 都写的是：网格 `y = -base..1-base`，**transform scale = (宽 m, 高 m, 1)**。门也是这个约定。
- 编辑器 `BuildMaterials` 实际做出来的网格，高度是 `aspect`（`y0 = -baseV * aspect`，`y1 = (1 - baseV) * aspect`），也就是“宽为 1、高为宽高比”。这种网格要用**等比缩放 (W, W, W)** 才对。

如果第 6 幕的包照 README 去设 scale = (W, H, 1)，卡的高度就变成 H × aspect。比如 Bank 的宽高比是 0.5，高度就只剩一半，形状整个压扁。这个约定是给后面所有幕的包用的接口，合进 main 之前必须统一。
**改法（二选一，推荐 a）**：
a) 和门一样：网格用卡的单位（x 是 −0.5..0.5，y 是 −base..1−base），scale = (W, H, W)，z 取 W 是为了让包围盒装得下转动的卡（见 R1）；
b) 网格保持现在的样子，把 shader 文件头和 README 改成“等比缩放 (W, W, W)”。

## 二、应改

### R1 · 包围盒：按 README 的 scale z = 1，卡转到侧面时会被视锥剔除，屏幕边上的卡会突然消失或出现
网格 bounds 的 z 范围是 1.5（局部单位），乘上 z 缩放 1 以后，世界里只有 ±0.75 m 厚。yaw 公告板转起来以后，卡在世界 z 方向的跨度能到 ±W/2，所以卡在屏幕边上时，包围盒已经出了视锥，卡还看得见，就会被剔掉、闪一下。门的 builder 是这么处理的：`localScale = (w, h, w)  // z = width: the bounds must hold the turning card`。和 B2 一起改。

### R2 · 网格没有按不透明框裁小：透明 overdraw 白白多了大约 1.5–2.5 倍
四边形用的是整张贴图。`opaque_bbox_uv` 已经量出来了，比如 Bank 只占 0.06–0.93 × 0.28–0.72（约 38 % 的面积），Cumulus 约 35 %。门把四边形裁到 alpha 框以后少了约 32 % 的 overdraw（VR r1）。圣经 §1.9 要求透明持续 ≤ 4 FSE，第 6b/6c 幕云墙、海、云盖会同屏。建议照门的 `CardQuad` 裁到 bbox，uv 也跟着裁。

### R3 · `_Melt` 的默认值是绝对米数，小卡会整张变成半透明
默认 (−10, 60)：从枢轴往下 10 m 到往上 50 m 之间做淡化。Puff 按 README 的建议是 20–60 m 宽，云体在 v 0.334–0.666 之间，40 m 宽的 Puff 云顶只比枢轴高约 13 m，那里的 alpha 只有 0.3 左右，整朵几乎看不见。Wisp 也会受影响；200 m 宽的 Cumulus，下面三分之一也被淡掉了。编辑器没有按卡单独设 `_Melt`。
**改法**：融化的高度改成按卡高的比例（比如在 shader 里用 sy 乘），或者编辑器按每张卡的尺寸写默认值，并在 README 里写清楚。

### R4 · 求解有退化：地光被抬到圣经 Trilight 地色的 3.07 倍，平的云底发出浅蓝的亮边
`card_solve.py` 的目标只管两件事：阴影体（10–30 百分位）和云顶（98 百分位）。天光 RGB 和地光增益都是自由的，阴影只约束了“天 + 地”的总和，具体怎么分没人管。解出来 `GroundColor = #8FA0BE 线性 × 3.07`，辐亮度 (0.84, 1.08, 1.58)。下半球均匀辐亮度 L 给向下的面带来的照度是 πL ≈ 2.6–5.0，比太阳的 E 3.1 还亮。另外日的色温停在了下界 2400 K（`Kmin`），说明解是被边界卡住的。

我量了云底那一条（不透明行最下面 4 %），和云体中位比：

| 卡 | rel 80° 底边 / 云体 | rel 150° 底边 / 云体 |
|---|---|---|
| Cumulus | `#A3B3C9` / `#97A2B4` | `#DBC9CB` / `#E9CCBA` |
| Bank | `#A2B4CB` / `#8F9CB2` | `#D9C9CC` / `#E8CBB9` |
| Puff | `#A8B5CA` / `#9AA4B7` | `#D7C8CC` / `#E8CCBC` |

侧光时，云底比云体亮、而且更蓝（底边 77–89 % 的光来自地光）。总览图上 80° 和 150° 两列，Cumulus、Bank 的底边都能看到一条发白发蓝的线。顺光时底边偏一点灰粉。这正是圣经说的“平底”毛病，只不过反过来了：底边在发亮。
**改法**：把地光增益钉住，或者加正则（比如 ≤ 1–1.2 倍 Trilight，或者按“下面的云原 / 海的反照率 × 日照”给一个物理上限），再把“底边不亮过云体”写进目标或量具里。重解以后再出一次总览图。

### R5 · 逆光时阴影偏丁香紫，离第 6 幕的上限只差约 0.5 C\*
按总览图同样的流程（叠在目标天上、S6、带 bloom），我量了卡上的像素：

| 卡 | rel 15°：h 290–330、C\* > 8、L\* > 40 的占比 | 色带内最大 C\* |
|---|---|---|
| Cumulus | 11.6 % | 11.5 |
| Bank | 10.1 % | 11.2 |
| Puff | 7.0 % | 11.0 |
| Wisp | 4.2 % | 10.2 |

第 6 幕的规则（h 285–330 且 C\* > 12）照字面是 0 %，量具报的 0 % 没有错。但余量只有约 0.5 C\*，而且 `cards_dawn.json` 里逆光的阴影中位是 Bank h 304 / C\* 9.4、Puff h 291 / C\* 10.1。放大看 Bank、Cumulus 的逆光格，靠近太阳的一侧云体是灰紫红的。这个颜色是蓝灰阴影和暖色 bloom / 天叠在一起来的（求解器自己的 rel 15 不带背景，量出来是 h 270）。第 6 幕的规则写着“晨不许有薰衣草”，到了 Unity 里，BC7、雾和真实的天一叠，很可能越线。
**改法**：求解时把 rel 15° 带背景、带 bloom 的阴影色相也加进目标（比如 h ≤ 280），或者在逆光权重上把天光往 h 270 拉一点。总览图的 json 里另外记一个 C\* > 8 的占比，方便看余量。

### R6 · 顺光到 110° 时，云体最暗处偏暖褐
求解器自己量的 rel 110° 阴影是 `#CDB1AC`（h 35、C\* 11），rel 150° 是 `#EACAB0`（h 66、C\* 18）。150° 时整朵都受光，可以理解。但 110° 时云的凹处还在阴影里，却是玫瑰褐，和圣经 §1.3 第 2 条“阴影里不允许出现暖色”、第 6 幕“云影绝不褐”不合。原因还是日色太强、太红（2400 K 卡在边界，R 6.57），三通道插值以后，阴影里也混进了不少日光通道。建议和 R4 一起重解，量具里加上 110° 的检查。

### R7 · D-25 的“亚像素淡化”做得太粗：前光时也会变暗，还可能在远处出一圈暗边
```hlsl
key *= 1.0 - _RimTame * (1.0 - kt.a) * saturate(texPerPx - 1.0);
```
- 它对所有角度都生效，不只是逆光。顺光、侧光时，半透明的边缘本来不比云体亮，也被压暗最多 60 %。而天光项没有跟着压，卡变小时，边缘会变成一圈偏蓝偏暗的轮廓。
- README 里说的是“往云体的亮度收”，实际代码只是乘了一个变暗的系数，并不是往云体的亮度收。
- 卡变小的时候，mip 本身已经在做平均了（贴图的边缘颜色向外推满过，所以 mip 里的边缘颜色还是亮的，这一点是对的，需要处理）。
**改法**：只按逆光通道的权重 `(1 - w1)` 去压；或者用 `tex2Dbias` / 高一级 mip 的 key 做 lerp，真正收向局部平均值。另外照门第 10 轮的做法，用 `measure_crawl.py` 在参考渲染上量一次爬行。shader 里的这一段 `cardshade.py` 没有移植，README 里“逐行移植”的说法要补一句这里不一样。

### R8 · `_Mirror` 自动模式在 rel ≈ 0° / 180° 会整张卡硬翻
README 也承认这个问题，说“由布局固定”。但第 6 幕的峡谷基本是朝着太阳开的（峡谷轴 40°，太阳 D-12 是 +30°），远端一整排逆光卡的 rel 都在 0° 附近，车一动就会翻。建议在 shader 里做一个 ±5° 的交叉淡化（镜像和不镜像各采样一次，按 sunRight 做 smoothstep 混合，只在这个窄带里多采一次），不要靠布局一张一张去固定。

### R9 · `_KScale.x = 6` 太大，浪费了约 1.3 bit，侧光通道只用了 80–98 个码
量出来白光通道的最大值：R 1.74–2.55，G 0.47–0.71，B 0.40–0.54（clip 都是 0）。按 6 去存，G 通道在云体上只用了 80–98 个不同的码（Cumulus 96、Wisp 80），再压成 BC7，侧光的大片阴影容易出色带。README 里“云顶 R ≈ 4 装不下”说的是乘过日色以后的数，可通道里存的是白光，日色在材质里乘，两件事混在一起了。
**改法**：kscale 用 3（Wisp 的 2.55 也装得下）；或者 R 和 G/B 分开缩放（`_KeyScale` 用 vec3）。sscale 1.5 也可以降到 1.1（S 的最大值 ≤ 1.01）。改完要重新导出 PNG，npz 不用重渲。

- `STATUS.md` 还写着“只有 Source/ 与 Docs~/，Unity 侧的东西还没有”，已经过时了。

## 三、建议

- **S1** 照上面把 `_SunDirFallback` 改成 (0.4973, 0.1045, 0.8613)。
- **S2** 编辑器读 `colours[Group(set)]` 时，如果暮组的卡先渲完、颜色还没解，会抛 KeyNotFound，整个 Build 中断，`SaveAssets` 也不会执行。建议缺颜色时跳过这张卡，记一行日志。
- **S3** 圣经第 6 幕正文（1130 行）写的是“受光顶屏幕 `#F3D2B0`”，色板写的是云顶 `#F6DCC4`。套件用的是色板的值，这没问题，但两个数不一样，请总导演定一个，或者在 README 里写清楚用的是哪个。
- **S4** 总览图用的是 npz（浮点），不是提交的 PNG。我量过误差很小（p99 ≤ 0.013），但最好直接读 PNG，这样量具量到的就是交付物。BC7 色带还是要等本地在 Unity 里看。
- **S5** `_Billboard 0`（世界固定的面板）：自动镜像只看太阳和视线，不看面板朝哪边。从背面看（Cull Off）时，贴图是镜像的，受光面会反。README 要写清楚：面板的 +z 要背向观看的人，或者这种模式下 `_Mirror` 必须手动设。
- **S6** yaw 公告板是竖直的，从上往下陡着看（第 6 幕在下降，云在“下方与四周”）会明显看出是一张薄片。卡是按略俯 0–4°（Strato 14°）烘的，建议 README 写一条：俯视角超过约 15° 的位置，用平铺 / 云原，不要用这些卡。
- **S7** duskD 的“另一批云”：`render_set` 里 `o * 0` 把噪声相位偏移关掉了，所以 duskD 的 Cumulus、Strato 只是 duskU 同一朵云镜像过来（再换个俯仰角）。而 shader 的 `_Mirror` 本来就会镜像，算不上“别的云”。暮组还在渲，不阻断，但请确认这是不是有意的。
- **S8** 逆光时卡的线性最大值有 12–18（`card_max_linear`），D-25 接受云顶微晕，但第 6 幕的包要用标准台按 D-09 量车门视向，VR 下 APL ≤ 150。

## 四、美术观感（总览图）

- **侧光（80°）**：四张积云类的阴影是 `#808EA5`–`#8895AA`，色相 270–271，和圣经的 `#8593AA`（h 272）对得很准，是蓝灰，不紫也不褐。受光顶 `#FAE2CE`–`#FBE3CE`，略亮略浅于 `#F6DCC4`，可以接受。但缩小以后整朵卡偏冷，桃金色只在右上一小块，“晨的受光面”不够明显。R4 / R6 重解的时候，可以顺带把受光面积做大一点。
- **顺光（150°）**：奶油桃色，最好看的一列，一眼就是晨云。毛病是底边有一条发白偏粉的线（R4）。
- **逆光（15°）**：云体是灰的，靠近太阳的一侧偏灰紫（R5）。银边很弱，基本被 bloom 吃掉了，读起来更像一块“挡在日出前面的灰剪影”，不太像“镶金边的晨云”。D-25 允许微晕，可以在调 R7 的同时让细边多留一点。
- 没看到黑边或白边、色带、硬切的平底；alpha 的边是软的。Strato、Wisp 透光多、阴影浅，这是对的。
- 陌生人能不能看出是“晨云”：顺光、侧光两列可以。逆光一列偏灰紫，需要 R5。
- 总的说：配色方向是对的，阴影终于是蓝灰了，比 v1 的薰衣草好很多。但这些都是在 numpy 里看到的效果，Unity 里因为 B1 会整张镜像。
