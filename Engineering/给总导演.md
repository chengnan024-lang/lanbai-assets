## 2026-10-22 · ⚠ PPv2 的 bloom 颜色在 Unity 里被“线性化两次”（影响 `Grading/`，请你定怎么改）

**发现**：独立 agent 拿 PPv2 3.4.0 的源码逐行核对标准台的 bloom 时查到的。`Bloom.cs` 第 211 行 `var linearColor = settings.color.value.linear;`，第 256 行 `uberSheet.properties.SetColor(ShaderIDs.Bloom_Color, linearColor);`——`properties` 是 MaterialPropertyBlock，而 `MaterialPropertyBlock.SetColor` 在线性色彩空间的工程里**会再做一次 sRGB → 线性**（Unity 文档原话：“The color value is considered to be always set in sRGB space and is converted to linear if the active color space is linear.”）。PPv2 自己的 `Fog.cs` 用 `SetVector` 传 `.linear`（不再转），Bloom 的调试叠加也用 `SetVector`，只有真正的 Uber 那一次走了 `SetColor`。
**后果**：白色不受影响；有色的 bloom 会比设计的更饱和。S8 `#FFE6CC` 设计的线性色 (1, 0.79, 0.60) 实际是 (1, 0.59, 0.32)——暮的日线、天缝周围的光晕会明显更橙；S6 `#FFF4E8` (1, 0.91, 0.81) → (1, 0.80, 0.62)；S4 `#F0F0F6` 会更偏蓝（0.87/0.87/0.92 → 0.73/0.73/0.83）；S4c、S7a、S9b、WHITE_BLOOM 也一样。
**证据强度**：源码两行是确定的；“SetColor 再转一次”来自 Unity 文档的说法（文档本站被代理挡了，是从镜像读的），Unity 的 C++ 不公开。**需要本地验一下**：S8 下放一个白色自发光方片（远超阈值），截一张 bloom 晕的颜色，和标准台的两种算法比。
**建议**：如果本地验证属实，`LanbaiGradeBuilder` 写 bloom 颜色时预先补偿：写进去的颜色 = LinearToGamma(设计的 hex)（这样两次线性化以后正好是设计值）。标准台已经按 Unity 的实际行为（两次）模拟，所以各包的参考图现在看到的就是 Unity 会出的颜色；Grading 改了以后我同步改标准台。
**顺带**：`grades_engine.json` 里 LENS_CLEAN 的 priority 两处不一致（`helpers` 199、`lens_desktop_only` 201），生成器已经取了 199（`LanbaiGradeData.cs` 第 44 行有注释），标准台也取 199，数据文件本身最好统一一下。
